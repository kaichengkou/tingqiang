# v0.7：Windows 客户端

测试机器：i7-13700HX（16 核 24 线程）、NVIDIA RTX 5060 Laptop 和 Intel UHD 双显卡、32 GB 内存、Windows 11。下面的数字只代表这一台机器。客户端内核是 Electron 45.2.1（Chromium 156.0.8078.75），同机 Chrome 是 156.0.8078.76，几乎是同一版引擎。

## 减弱伴奏的等待时间

模型每块输入约 5.9 秒音频，推进约 4.4 秒。单块耗时：

| 方式 | 每块 | 所有进程内存峰值 |
| --- | --- | --- |
| WASM 1 线程 | 12.5 秒 | |
| WASM 4 线程 | 4.1 秒 | |
| WASM 8 线程 | 3.1 秒 | 1.4 GB |
| WASM 12 线程 | 2.7 秒 | |
| WASM 16 线程 | 2.4–2.7 秒 | 1.5 GB |
| WASM 24 线程 | 2.7 秒 | 1.5 GB |
| 4 个 Worker，各 1 线程 | 3.8 秒 | 4.3 GB |
| 8 个 Worker，各 1 线程 | 6.0 秒 | 8.0 GB |
| 12 个 Worker，各 1 线程 | 6.2 秒 | 11.7 GB |
| 16 个 Worker，各 1 线程 | 渲染进程崩溃 | |
| WebGPU，Intel UHD | 3.8 秒 | |
| WebGPU，RTX 5060 | 0.22 秒 | |

所以 CPU 上用一个会话配多线程，上限 12（再多几乎没有收益，还抢播放的资源）；有好显卡就用显卡。Chromium 默认只把绘制界面的 Intel 核显交给 WebGPU，`powerPreference` 和 `use-webgpu-power-preference` 都不起作用，只有启动参数 `force_high_performance_gpu` 能换成 RTX 5060。

真实录音《三家店》（112 秒 MP3，于魁智）的全流程耗时：

| 环境 | 耗时 | 处理时播放卡顿（欠载） |
| --- | --- | --- |
| 网页版，Chrome，1 线程，没有播放 | 604.5 秒 | |
| 客户端，RTX 5060，没有播放 | 13.5 秒 | |
| 客户端，RTX 5060，首次运行，同时降调播放 | 18.1 秒 | 0 次／播放 15 秒 |
| 客户端，只用 CPU（12 线程），同时降调播放 | 99.4 秒 | 0 次／播放 98 秒 |
| 客户端，限 4 个逻辑核（2 线程），同时降调播放 | 307.5 秒 | 0 次／播放 304 秒 |

限核是用进程亲和性模拟的弱机器，CPU 型号仍是这一颗，不等于真实的老电脑。卡顿数据来自 `AudioContext.playbackStats`。

上限长度：10 分钟合成曲目，RTX 5060 上分离 139.8 秒，加上重新分析人声共 198.5 秒，所有进程内存峰值 4.0 GB。

结果与后端无关。同一段 20 秒输入，以单线程结果为基准：

| 对比 | 伴奏信噪比 | 人声信噪比 |
| --- | --- | --- |
| 12 线程 | 135 dB | 139 dB |
| WebGPU（RTX 5060） | 127 dB | 132 dB |

差异在浮点舍入量级，听不出来。

显卡不能用时的表现：

| 情况 | 结果 |
| --- | --- |
| 显卡太慢（Intel UHD，第二遍 3.8 秒） | 改用 CPU 完成。这次试跑多花约 11 秒，记住后不再试 |
| WebGPU 运行文件缺失 | 改用 CPU 完成，下次仍会尝试 |
| 处理中杀掉 GPU 进程 | 检测到设备丢失，用 CPU 从头完成（78 秒）；下次又回到显卡（12.2 秒） |
| 没有 GPU（`--disable-gpu`） | 直接用 CPU |

GPU 丢失这一项最初的实现会永远卡住，进度条停在原处，是实测杀进程才发现的。现在 Worker 同时监听设备丢失和 30 秒无响应。

## 其他等待

- 《三家店》：导入后 1.3 秒可以播放，13.2 秒完成音高分析。只用 CPU 的 30 秒合成录音：客户端约 4.3 秒，Chrome 约 3.9 秒。两者的差异与跨源隔离无关（开关对照结果相同）。
- 启动：从启动到页面加载完成约 0.8 秒（程序文件已在系统缓存中，开机后第一次会慢一些，未测）。
- 安装包 168 MB，安装后 414 MB，静默安装 12–39 秒。内存：空闲约 390 MB，分析后约 1 GB（Worker 保留 2 分钟），用显卡分离时峰值 3.2 GB。

## 跟着伴奏唱

软件回环（方法见 [validation-v06.md](validation-v06.md)）在打包后的客户端里跑两次的范围，校准测得回环自身约 11–21 ms：

| 情况 | 偏差 |
| --- | --- |
| 原速原调 | 15–25 ms |
| 合成回放，人声与伴奏 | 3–10 ms |
| 下载合成 | 10–20 ms |
| 降调 | 15–25 ms |
| 降调的下载合成 | 10–20 ms |
| 0.75× 慢速 | 15–25 ms |
| 首句（静音倒数） | 5–25 ms |

这和 v0.6 在 Chrome 中的范围一致。真实麦克风只验证过能打开并有信号（48 kHz，AEC 关闭，1 秒，只算电平，未保存）。

用真实录音走通了完整流程：导入、分析、导入 LRC（16 句）、减弱伴奏、切到伴奏、跟唱一句（麦克风用 Chromium 的文件模拟设备）、蓝线叠加。

## 客户端专项检查（tests/desktop.mjs）

下面都在打包后的程序上运行：

- 沙箱：页面没有 Node，只有三个桥接方法；只能拿到音频，摄像头被拒；外部网址和其他 host 无法连接；路径逃逸（`..`、`%2e%2e`、`..%5c`、`%00`、目录）一律 404；POST 返回 405；打开本地文件的导航和新窗口都被拦下。
- 网络：运行分析和分离时，程序的所有进程都没有非回环 TCP 连接。
- 打开文件：命令行参数、第二个实例转交、系统「打开」对话框。MP3、M4A、FLAC、OGG 都能解码和播放；不支持的文件和不存在的路径被忽略；.lrc 能导入唱词；.tqproj 能在另一个配置目录恢复。启动时打开的文件不会被恢复上次练习覆盖。
- 重启：正常关闭和强杀之后练习都在；`navigator.storage.persisted()` 为 true；窗口位置保存。
- 系统对话框：保存时给出练习名（含中文）并写入文件；录音中关窗先询问，选「继续」后录音不中断，选「退出」后程序结束；渲染进程崩溃时提供重新打开，并恢复已保存的练习。
- 麦克风被禁止或不存在时有对应提示。「打开麦克风设置」按钮的显示验证过，但没有实际点击。
- 窗口最小化时动画帧降到约 1 帧／秒，循环和跟唱逻辑改由定时器驱动：A-B 循环不会跑出选段，跟唱到句尾自动停止，录音长度正确。

## 安装程序

向导是中文，图标正确。装到带中文和空格的路径后，桌面和开始菜单快捷方式、文件关联都正确；从安装目录运行，分析和分离正常；真实双击 .tqproj（经系统文件关联）能导入练习。卸载后程序、快捷方式、注册表项全部清除，数据目录不动。electron-builder 自带的关联有两处问题已用 desktop/build/installer.nsh 修正：程序路径没加引号；卸载后 .tqproj 仍指向已删除的类。

## 回归

72 项单元测试、Python 服务 8 项全部通过。browser、browser-pitch、browser-timing-lyrics、browser-studio、browser-singalong、browser-separation 在 Chrome 和打包后的客户端里各跑了一遍，全部通过。browser-separation 用真实模型补跑了一次，v0.6 没有运行过它。famen-recording 需要一份特定录音，用户的曲库里没有哈希匹配的文件，未运行。

## 没有验证

- 真人演唱，以及真实耳机和蓝牙的延迟。
- 用电池时不选独显：这台机器测试时一直接着电源，这条路径只是按代码推理。
- 其他机器：AMD 显卡、较老的 NVIDIA 显卡、真实的低配电脑、Windows 10。
- 从网上下载安装包时 SmartScreen 和杀毒软件的反应（本机构建的文件不会触发），以及从旧版本升级安装。
- 减弱伴奏对各类京剧录音的实际听感。这里验证的是后端一致性和流程，不是分离质量。
