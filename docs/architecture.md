# 基础版本结构

## 音频与时间

前端的参考音源使用一个 HTMLAudioElement，自己的录音使用另一个。首次播放时两者连接同一个 AudioContext；参考音源经 PitchOutput 路由，可在直通与 Signalsmith Stretch 工作节点之间切换，自己的录音直接输出。切换声部时保持原录音时间和播放速度；曲线、歌词和循环点统一使用原始参考秒数。慢放使用浏览器的 preservesPitch，曲线坐标不随播放速度改变。

显示时钟每个动画帧只计算一次，供曲线、当前音高、字幕和概览共用。优先用 AudioContext.getOutputTimestamp() 将渲染时间换算为设备输出时间，缺失时使用 baseLatency + outputLatency；按播放速度折算延迟后从媒体时间扣除。降调时另扣 Signalsmith 报告的处理延迟。手动偏移是实际播放毫秒，正数提前画面，范围 ±1000 ms；慢放也按播放速度换算。自己的录音按 anchor + offset + recordedSeconds × recordedRate 映射；回听速度为当前练习速度除以录制速度。浏览器未报告的蓝牙／系统延迟仍可能需要用户微调。

各音源只保留文件 Blob 和播放地址，另记时长与波形概览；不常驻解码后的 PCM。导入时以 8 kHz 临时解码取时长和概览；分析、分离时才按所需采样率（12／16／44.1 kHz）临时解码，用完即释放。保存的练习带有概览，打开时无需解码；旧练习或导入的练习包首次打开时补算一次。

原声、分离人声、分离伴奏各为独立音源。手动分轨检查长度，但不能仅凭长度验证内容是否对齐，需使用同起点的音频。三个声部切换只影响听到的内容，不改变曲线分析来源。

曲线优先使用已分离人声；原录音可以直接分析，界面始终显示实际来源。切换分析来源或调整音域后需重新分析。

## 音高分析

默认使用 CREPE tiny。解码时直接重采样至 16 kHz 并下混为单声道；每个 Web Worker 用自托管 ONNX Runtime WASM 单线程推理。1024 样本窗按当前时刻居中，两端补零，每 20 ms 一帧；按上游 torchcrepe 的无偏标准差归一化。

360 个音高 bin 按每格 20 音分覆盖约 32–2006 Hz。在允许音域内做三角转移的 Viterbi 跟踪，再在选中 bin 附近 ±4 格按原始激活值加权，得到连续频率；不加入随机抖动。音域裁剪只屏蔽观测，转移归一化保留完整模型音域，避免跟踪器被裁剪边界吸引。

默认置信度门限 0.12，三帧中值仅用于有声判断；低置信度、低音量和短于三帧的孤立小岛留空。没有对音高进行大范围平滑。模型输出以 8-bit 激活缓存，再解码，降低长录音内存。此置信度是模型周期性分数，并非唱腔准确率。

帧彼此独立，PitchPool 把每约 4 秒一块分给最多 4 个 Worker（只用普通消息传递，不要求跨源隔离），优先计算播放位置附近；响度低于 0.002 的帧不进模型。每块先做一次局部跟踪用于边算边画，全部完成后再对全曲跟踪一次，这才是保存的结果，所以中途显示不写入练习。录音时暂停派发，避免抢占音频。

音高点仍为 `{t, hz: number|null, confidence, rms}`，时间单位为原录音秒数。传统 YIN 思路的 12 kHz 快速周期分析保留为可选方式。用户清唱样本的对照记录见 validation-famen.md。

主图固定当前播放时间在中央，默认 8 秒，可选 4／16／32 秒。起点为 `currentTime - window/2`，不在曲首或曲尾夹紧，所以边缘允许留白。每个播放帧连续更新，不再按段翻页。选段拖动期间固定视野便于操作，松手后恢复跟随。底部概览仍显示整曲。

## 学唱曲线（v0.3）

模型输出原样保存在 state.analysis。显示层 practice-curve.mjs 单独生成 state.displayAnalysis，不改变置信度门限、原始识别点和分析统计。默认在半音坐标中做两次 5 点二次局部拟合，保留滑音斜率和大部分 3–8 Hz 颤动。没有逐句平均或把旋律压成音阶。

只连接两端均有识别点、缺口不超过 0.2 秒、音差不超过 3.5 半音且没有明显静音的区间；以对数音高插值并标记 interpolated。图上以浅色显示，悬停和当前音高会注明参考连接。长停顿、曲首曲尾、大跳变和真实静音保留空白。

绘图用形状保持的单调三次曲线，局部极值处切线归零，并限制斜率避免过冲。显示参数调整只重建显示层，不重新运行模型。选择原始识别会禁用短缺口连接。

## 浏览器伴奏抑制（v0.4，实验）

用户主动点击后，原录音在本机重采样为 44.1 kHz 双声道，传给独立 Worker。下载固定版本的 UVR_MDXNET_KARA_2（52,786,726 字节），SHA-256 验证通过后才加载；CacheStorage 只保存公开模型，不存音频。

复用 MIT 的 web-audio-separation 和 PFFFT STFT/ISTFT，网页版的模型由现有 ORT 1.20.1 单线程 WASM 运行（客户端见上文）。参数为 FFT 5120、hop 1024、dim_f 2048、256 帧、25% 重叠。模型估计伴奏，再在同一音量域从原声求差得到人声；补偿和输出共同增益在 stem-mix.mjs 中处理，避免声部各自归一化改变比例。

支持不超过 600 秒的录音，下载约 53 MB，CPU 较慢。模型工作区按约 23.8 秒的主段处理，前后约 2 秒上下文，约 93 ms 交叉渐变；主段和上下文起点对齐 1024 样本 hop。全曲只计算一次归一化峰值，输出回写原始样本下标，最后才统一增益。分块限制 STFT／模型工作区，完整输入、输出和播放音源仍随曲长占内存，长段建议电脑。未承诺处理速度或全设备 10 分钟实测。

处理过程中仍可播放原录音；取消会停止 Worker 和下载，保留现有音源。成功后一起替换两个声部，保持时间，自动选择人声分析。可用本地 Demucs 服务处理更长段。京剧伴奏条件尚未有独立测试集，不能保证京胡完全去除。

## 增强服务 API

- `GET /api/health`：是否可用、分离依赖状态。
- `POST /api/jobs`：multipart 的 `file` 字段，返回任务 id。
- `GET /api/jobs/{id}`：queued／running／done／failed／cancelled 和说明。
- `GET /api/jobs/{id}/vocals.wav`：人声。
- `GET /api/jobs/{id}/accompaniment.wav`：伴奏。
- `DELETE /api/jobs/{id}`：取消、删除临时任务数据。

调用 Demucs 的 `htdemucs` 双声部输出；源文件不写入静态发布目录。后台一次处理一段，最多接受两个待处理任务。分离器在 `process_job` 中，可替换为 UVR／MDX 等方案，前端不需改动。

静态 Sites 仅承载前端；增强服务必须在可运行 Python／PyTorch 的机器上运行。私有发布没有自动上传录音或调用付费 API。

## 练习状态与数据（v0.5）

Studio 管理逐句练习、录音和保存，主 app 保留音源与图形。IndexedDB（v2）的 projects 只存练习状态，analyses 按项目与 reference／take:录音 ID 存原始分析，shelf 存轻量索引，assets 按项目与声部／录音 ID 存 Blob。一次事务提交状态、索引和变动的音源与分析；分析只在重新分析或新录音后写入，位置／调门等更新只重写很小的状态记录。由 v1 升级时，一次性把内嵌在 projects 里的分析移到 analyses。保存失败明确显示未保存。自动保存去抖，播放时约每五秒保存位置，暂停及编辑时补充保存。刷新恢复最后练习。删除练习清理索引、状态和其全部音源；删除当前练习同时卸载播放数据。

.tqproj 为有版本的二进制容器：8 字节魔数（TQPRJ01 后接换行）、4 字节 little-endian JSON 长度、JSON 元数据、顺序 Blob 数据。不压缩音频，构造 Blob 时不整包读入内存。导入校验魔数、元数据／总大小、资产长度、重复键、必需音源、曲线时间与频率、歌词及校音字段，再创建新项目 ID；不执行导入内容。

逐句练习按现有 LRC 时间、明确句尾和录音长度界定区间。重复听或听唱交替的阶段由 requestAnimationFrame 驱动，留白使用单调时间；停止、换句和更换速度会取消当前练习。听完先等待输出尾音，再开始跟唱倒计时。

录音先请求 getUserMedia，三秒准备后启动 MediaRecorder，暂停参考音源，无麦克风监听。以当前句／选段起点、播放速度和调门记录元数据；到选段末尾自动停止，最多两分钟。停止后释放轨道，先保存音频，再用独立 CREPE Worker 分析。模型失败仍可回听已捕获音频。蓝线按录制时的速度和用户偏移映射到参考坐标，保留实际音高，不按调门自动修正自己的声音。曲线及音源可独立切换。

## Windows 客户端（v0.7）

desktop/ 是 Electron 外壳，dist/ 原样放进安装包，不复制页面逻辑。页面通过 `window.tingqiangDesktop` 判断自己在客户端里，只改几处提示，隐藏增强服务，并接收系统打开的文件。网页版不受影响。

页面从私有协议 `tingqiang://app/` 加载，而不是 file:// 或本地端口。这样源固定，练习数据不受安装位置和端口影响；它是安全上下文，可以用麦克风；还能带上 COOP／COEP，从而启用多线程 WASM。

安全边界：页面运行在沙箱里，没有 Node；预加载脚本只暴露三个方法，主进程再次校验调用来源；只放行麦克风（不含摄像头）；CSP 和主进程请求拦截两层禁止任何外部连接；导航和新窗口都被拦下，只有 http(s) 链接交给系统浏览器。协议处理器只提供 web 目录内的文件，以及用户明确打开的文件（一次性随机地址）。

打开文件有三条路：命令行参数（含文件关联）、第二个实例转交、菜单 Ctrl+O。它们都进入同一个队列，等页面恢复完上次练习后再交给它，所以刚打开的文件不会被覆盖。

构建：scripts/build-desktop.mjs 在 OneDrive 外的目录同步源码、校验模型 SHA-256，再调用 electron-builder。

### 减弱伴奏的后端

每块模型输入约 5.9 秒，推进约 4.4 秒。按优先级：

1. 显卡（WebGPU）。Chromium 只把它绘制界面用的显卡提供给 WebGPU，笔记本默认是核显，所以接着电源时启动参数选高性能显卡；用电池时不选，否则独显会在程序打开期间一直醒着。先跑两遍模型测速，第二遍超过 3 秒就判定不如 CPU，记住这块显卡以后不再试。
2. CPU 多线程 WASM。一个模型会话配最多 12 个线程，并留两个核给播放。不用多个 Worker 各跑一个会话：每个约占 1 GB，超过 4 个反而更慢。

显卡丢失或 30 秒无响应时，模型的 Promise 永远不会结束，因此 Worker 同时监听 `device.lost` 和进度，一旦触发就用 CPU 从头重做。试跑通过之后才丢失的，可能只是驱动的偶发问题，下次还会再试。

两种后端用不同的 ONNX Runtime 文件：WebGPU 版的 WASM 大一倍，所以 CPU 路径继续用普通版，separator 也打了两份包。客户端把分块上限放大到约 190 秒，减少重复计算块间重叠的时间。

## 安卓 App（v0.8）

android/ 是一个只有 WebView 的外壳（Java，没有 AndroidX，也不用 Gradle），dist/ 原样放进 APK 的 assets。页面用 `lib/shell.mjs` 判断平台：Windows 客户端和安卓 App 都有原生桥，页面只问 `platform` 和 `shell`，不直接探测全局对象。

页面从 `https://appassets.androidplatform.net/` 加载，这是安卓为此保留的域名：App 在 `shouldInterceptRequest` 里从 assets 读文件作答，其他地址一律返回 403。源固定，练习数据跨版本保留；https 让麦克风可用。App 不申请 INTERNET 权限，CSP 与 Windows 客户端相同，所以录音无处可去。COOP／COEP 头照样发送，但 WebView 不支持跨源隔离，页面拿不到线程（docs/validation-v08.md）。

原生桥（`MainActivity.Bridge`，页面里叫 `tingqiangAndroid`）只有这些：页面就绪、打开文件、麦克风状态和设置页、保持亮屏和后台工作、导出文件、运行分离模型、版本信息。它们都在 WebView 自己的线程上被调用，凡是碰界面的都转回主线程。

### 文件

- 选择文件：系统选择器给的是 content:// 文件，WebView 报的大小是 0。App 先把它复制到缓存，再把普通文件交给页面；IndexedDB 保存时会自己复制一份，所以下次启动时清掉缓存不影响练习。
- 别的应用交来的文件（打开方式、分享）：同样复制进缓存，以一次性地址 `/__opened/<随机>` 交给页面，与 Windows 客户端的队列一样等页面恢复完上次练习。.tqproj 和 .lrc 没有注册的类型，按文件名匹配。
- 导出：手机没有下载文件夹，`studio.download` 在 App 里改为分块交给原生（base64），再由用户选「发送给…」（系统分享面板，文件由 `SharedFiles` 只读、按次授权）或「保存到手机…」（系统保存界面）。

### 后台

按 Home 或锁屏后，安卓几秒内就会冻结 App 的页面。页面每秒报告一次自己在做什么：播放、练习、跟唱算「播放」，分析和减弱伴奏算「处理」。有事时 App 保持亮屏，并启动前台服务（`BusyService`）：播放用媒体播放类型，处理用媒体处理类型（Android 15 以前用数据同步），处理时另持有部分唤醒锁。空闲 5 秒后才结束，免得逐句练习的间隔把它停掉。渲染进程优先级设为不可见时也不降低。录音例外：安卓不让后台应用用麦克风，所以页面离开屏幕时结束录音并保留已录部分。

App 不请求通知权限（声明了，用户可在系统设置里打开）；没有它，前台服务照样工作，只是通知栏不显示进度。

### 减弱伴奏

页面里的 WASM 只有一个线程，手机上一首两分钟的唱段要十几分钟。App 用 ONNX Runtime 安卓版（1.31.1）在 4 个核上跑同一个模型：

1. 页面为分离 Worker 建一条 MessageChannel。Worker 加载 `vendor/separator-native.mjs`，这是 separator 的第三份打包，其中 onnxruntime-web 换成了 `lib/native-ort.mjs`。
2. 每一遍模型输入（约 8 MB）由 Worker 发给页面，页面分块交给 App（`NativeModel`），App 在自己的线程上运行，完成后回调页面，页面从 `/__model/<id>` 取回二进制结果交还 Worker。
3. 短时傅里叶变换、分块、交叉淡化和合成仍在页面里，与浏览器和 Windows 用的是同一份代码，所以结果一致（实测 127–134 dB）。

没有原生库的手机（32 位）退回：先试显卡，再用 WASM 单线程。原生模型加载失败也会退回 WASM。音高分析在手机上最多两个 Worker，减弱伴奏开始前关掉空闲的 Worker：三个 ONNX Runtime 实例同时存在时，渲染进程会因内存映射失败而崩溃。

ONNX Runtime AAR 自带的清单申请 INTERNET 并注册遥测组件；这里不合并第三方清单，两者都不进 App，遥测不会启动。

### 返回键、转屏和崩溃

返回键先交给页面：关掉最上层的窗口，否则结束录音或练习；页面没用上时 App 退到后台而不结束，回来时页面原样。转屏、改字号等配置变化不重建 Activity，页面不重新加载；文字跟随系统字号，最大 130%。页面进程崩溃或被系统回收时，App 新建 WebView 并恢复上次练习；20 秒内再次崩溃则先询问。

### 构建

scripts/build-android.mjs 直接调用 SDK 工具：aapt2 编译资源和清单，javac（Java 8 语法）和 d8 编译代码及 ONNX Runtime 的 Java 部分，jar 加入 assets、原生库和 dex，zipalign，apksigner 签名。assets 不用 aapt2 的 `-A`：在 Windows 上它把路径写成 `assets/web\index.html`，安卓找不到。工具链、模型和输出都在 OneDrive 之外。

## 跟着伴奏唱（v0.6）

麦克风接入播放用的同一个 AudioContext，由 AudioWorklet（capture-worklet.mjs）逐块采集，经零增益节点接到输出以保持运行，不会出声。不用 MediaRecorder：它的起始时刻不可知，编码器还有起始延迟。

时间关系（sing-along.mjs）：播放时反复读取「媒体时间 − 速度 × 音频时钟」并取中位数，得到媒体时间与音频时钟的换算；第一个采样在原录音上的位置 anchor = 换算值 + 速度 ×（采集起点 − 往返延迟 − 移调延迟）。往返延迟优先用拍手校准的结果（存于本机，换设备失效），否则用浏览器报告的输出延迟加输入延迟。此后沿用原有映射：参考时间 = anchor + offset + 录音秒数 × 速度。

流程：选段起点提前 2／4／8／16 秒播放所选音源（伴奏优先，没有则原声）；可用的前奏不足 2 秒时补静音和提示音倒数。图上提示倒数和下一句，并用单帧模型结果实时画蓝线；选段结束后 0.5 秒自动停，也可手动停。保存为 16 位单声道 WAV，再按普通录音走完整分析。结束或取消都恢复原声部、选段和循环状态。

「合成」回听时伴奏走主播放链，人声元素跟随它：偏差超过 15 ms 用 ±3% 内的速度微调追赶，超过 250 ms 直接跳转。「下载合成」用 OfflineAudioContext 渲染；有移调或变速时伴奏经 Signalsmith Stretch 处理，人声按其输出延迟错开。默认人声音量按原唱与这遍录音的响度比估算，可调。

## 节拍和唱词

从原录音的短时能量上升估计固定节拍，有稳定周期才返回结果。不是专业打击乐／京剧板眼模型，不能推断板式，也没有可变速度节拍图。手动点拍／BPM 网格用于初次验证体验。

LRC 按已给定的时间在曲线下方显示当前句；增强 LRC 支持 `<mm:ss.xx>`，文件中的每个标记可以是一字或一词；保留首个字标前的正文，末尾空字标或空 LRC 行可结束上一句。TXT 不做强制对齐，只提供逐句手动标记。所有导入文本、注音和候选都通过 textContent 渲染。字幕显隐偏好保存本机。

“从首句唱起”优先使用最早有效唱词时间（含全篇偏移）；否则检测分析结果首个持续至少 180 ms 的有声区，允许短缺口、忽略孤立尖峰，并留 120 ms 预备。此按钮关闭当前循环并开始播放。检测依据是所选声部的音高，原声中的乐器可能影响估计。

## 上口／尖团字参考

dist/data/opera-pronunciation.json 来自用户提供旧项目 HTML 的 DATA 字面量，未执行上传代码。尖团表含 1324 字（其中 485 尖字），上口表含 804 字；保留多读法、韵部、声调类别和原始拟音。普通话用自托管 pinyin-pro 的上下文注音；上口候选优先于尖字候选，缺失读法明确显示待校订。

一字一条注音结果，含出现位置、原字、普通话、候选、来源、isUpper 和特殊标记。v0.4.1 起仅 isUpper 且仍采用特殊读法的汉字使用红色 ruby/rt 和点线，其他字渲染普通文字；句子不整体染红。曲线字幕与唱词列表共用渲染器，逐字时间跟随仍通过词容器的中性底色表现。普通话与仅尖团差异的注音仍可在「校音」查看。按句「校音」可覆盖该次出现的读法和特殊标记；不会修改字库或其他相同字。时间与字音校订随练习保存在本机。此字表提示不代表识别到了演唱者的实际读法，需按字义、唱段和流派校订。
