# v0.6：减少等待与跟着伴奏唱

## 等待时间

音高模型每帧独立，分块交给多个普通 Worker，无需 SharedArrayBuffer 或特殊响应头；最后仍对全曲做一次连续跟踪，结果与单线程相同。单元测试用乱序返回验证了组装结果和跟踪结果一致。

本机 Chrome（24 逻辑核）分析 60 秒合成唱段：

| Worker 数 | 总耗时 | 第一段曲线出现 |
| --- | --- | --- |
| 1 | 19.2 秒 | 1.6 秒 |
| 2 | 10.9 秒 | 1.9 秒 |
| 4 | 6.6 秒 | 2.3 秒 |
| 8 | 5.2 秒 | 3.0 秒 |

超过 4 个收益很小，上限定为 4（至少留一个核，低内存设备 2 个）。这些是单台桌面机的数字，手机未实测。

- 导入后自动分析，期间可播放、定位；曲线边算边画，优先计算播放位置附近。端到端实测 30 秒录音从导入到第一段曲线约 2.5 秒，到分析完成约 3.5 秒（8 次均在 3.8 秒内），全程在播放。
- 响度低于 0.002 的帧不可能产生音高，跳过模型。真实模型对照：合成示范人声逐帧完全一致；长段近静音的录音只需运行 697／1201 帧，省约 42% 时间，1 帧边界有差异，共同帧最大差 10.4 音分。
- Viterbi 转移代价改为查表，该阶段约快 3.8 倍。
- Worker 保留 2 分钟供下一次分析复用，所以录完一遍后的分析不再重新加载模型。

未处理：浏览器分离仍是单线程。上游资料显示 WebGPU 可能大幅提速，但需用真实模型实测后才能启用。

## 跟着伴奏唱

麦克风在播放用的同一个 AudioContext 内由 AudioWorklet 采集，不经 MediaRecorder，所以没有编码器起始延迟，每个采样都在伴奏的时钟上。播放期间持续记录媒体时间与音频时钟的关系，取中位数；再扣除输出、输入和移调处理延迟，得到这遍录音在原录音上的位置。

用软件回环代替歌手（送往扬声器的声音直接接回录音入口），先用延迟校准测出回环自身约 11–21 ms，之后连跑 8 次的范围：

| 情况 | 曲线与原唱的偏差 |
| --- | --- |
| 原速原调 | 15–25 ms |
| 降 3 半音（含 120 ms 移调延迟） | 15–25 ms |
| 0.75× 慢速 | 15–30 ms |
| 合成回放，人声与伴奏 | 1–4 ms |
| 下载合成，原调／降调 | 10–20 ms |

回环只验证时序模型和内部链路，**不能代表真实耳机、声卡和蓝牙的延迟**，也没有经过真人演唱检验；真实设备上若有偏差，用延迟校准或对齐偏移修正。iOS、安卓和 Firefox 均未实测。

其他已验证：倒数与首句提示、演唱中实时蓝线、提前进入不足时的静音倒数、停止与取消后恢复选段、自动对齐（把 1.5 秒的人为偏差修回 0–0.02 秒）、拍手校准的识别算法（含漏拍和乱拍的拒绝）、刷新恢复且不重跑模型、手机布局不溢出。
